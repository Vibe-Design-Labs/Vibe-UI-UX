# 社区、可复用实现与多端联动方案

更新日期：2026-10-13。公开站点基线为 `0.4.1.2.1`，本轮待审开发版本为 `0.4.2.0.0`。本轮先完善 Web、实际组件导出与维护流程；插件和 REA 明确暂缓。未合并 PR 和完成 Pages 部署前，不视为官网上线。

## 1. 当前实际状态

- 已有：静态官网与工作台、75 个词条的专属预览、受控参数、描述与 JSON、5 类本地编译配方、可选 TokenDance、维护 skill、MIT 代码与 OFL 字体。
- 本轮待审实现：双版本贡献指南、案例模板与署名索引；5 种效果的共享渲染、独立 Web 示例、React 组件 / hook 和 Remotion 视频工程。索引暂时为空，不表示已有社区投稿。详见 [代码导出与验证边界](WEB_COMPONENTS.md)。
- 尚未实现：运行时作者徽章、社区作品投稿系统、可安装浏览器扩展、截图/录像参考导入、所有 75 个词条的组件导出、PWA 离线安装、移动 App、跨设备账号同步、REA 连接与 MCP 服务。
- 已配置远程 main 保护：PR 审核、过期审核撤销、CODEOWNERS 审核要求、对话解决、线性历史、禁止强推 / 删除，开启管理员保护；仅维护者 virtue192 保留人工发布例外与写入权限，自动合并关闭。CODEOWNERS 与只读 PR CI 文件随本轮 PR 交付。必需状态检查在真实 PR 检查成功后绑定；实际状态以 GitHub 设置为准。

## 2. 社区采用维护者策展的方式

```text
私信提案
  → 维护者确认准备方向
  → 作者在自己的 Fork 做案例 / 源码 / 证据
  → PR 或 Draft PR
  → 自动检查提供证据 + 维护者人工判断
  → 手动合并
  → Pages 部署成功后公开体验
```

方向确认、自动检查、合并审核、知识审校与部署是不同阶段。核心任务是降低贡献难度，又让每条公开内容保持可理解、可运行与可验证。

启动时不必先建立账户、积分或作品数据库：GitHub 存储源码、版本与评审过程，私信用于提案沟通，案例文档与索引用于署名。未来作者数量增加时，再讨论将已接受案例索引转为网站读取的数据。

已经采取的审核约束：

1. 普通贡献者通过 Fork / PR 提交，不因投稿获得官方写权限；自动合并保持关闭。
2. main 需要 PR、1 个审批和 code owner review；变更后旧审批失效，禁止强推和删除。
3. 单维护者仓库保留 virtue192 的明确例外：自己的 PR 无法自审，维护者仍可人工决定发布。该例外不意味着允许其他投稿自动合并。
4. 新的 PR 检查只读、无项目密钥，采用 pull_request，不执行高权限 pull_request_target。PR 阶段不部署。
5. 本轮首个 PR 验证成功后启用必需检查；CODEOWNERS 在合并后才成为 main 上的规则文件。自动检查提供证据，不能代替人工判断。

分支规则仍需维护者持续核对。[GitHub 分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

## 3. 「关联仓库提供实现起点」具体指什么？

一个作品关联可运行代码，使用者就不必仅凭视频重新猜实现。他可以打开入口、安装必要依赖、调整参数，并将适用部分接入自己的项目。仓库里的效果代码可能可以复用，但不一定已经是适合所有框架的组件，也不保证原视频与复刻完全一致。

实际例子：`vibe-motion/fisheye-motion` 的 README 给出框架无关的 WebGL 渲染器、React 封装与 Remotion 视频工程，同一底层实现可用于交互与视频。它展示了比纯视频参考更具体的实现路径。这里只核对官方说明，没有安装执行，也未确认可用于我们项目的复用许可；本文不复制其源码。[示例仓库](https://github.com/vibe-motion/fisheye-motion)

本轮将 5 个受控模板整理成可独立运行的 Web、React 与视频工程，其他词条仍只有相应预览和设计 JSON。不能将首批组件导出说成全部效果都已生产验证。官方仓库整体可运行，不等于用户能一键把指定效果放入任意项目。

### 我们可以在哪些方面做得更好？

将「源码链接」逐步提升为「有运行方式、参数对应表与验证结果的实现案例」：

| 需要的信息 | 如何帮助使用者 |
| --- | --- |
| 原作者与具体版本 | 知道谁贡献、复现哪个 commit/tag，避免链接更新后行为变化 |
| 最小运行方式与入口 | 快速找到实际实现，区分演示框架与效果模块 |
| 参数对应表 | 预览中的 px、ms、色值对应代码中同名或明确映射的参数 |
| 支持的平台与限制 | 明确原生 Web / React 等范围，不承诺未实现的 Vue、Flutter 或全平台支持 |
| 适用任务与替代行为 | 知道什么时候用，以及键盘、触摸、减少动态效果如何处理 |
| 默认与极值验证 | 能核对预览、描述、JSON 与实现是否一致 |
| 许可与素材清单 | 明确代码和素材各自的复用条件，公开仓库不自动等于 MIT |

本轮从暖金聚光与抬升试点抽离共享核心，再覆盖 5 类配方对应的受控模板。已比较工作台、原生示例和 React 的同参品牌演示，并实际渲染试点视频；后续模板仍需逐项验证，不能只凭共享参数契约声称画面一致。

最小验收：同一组参数在工作台、导出描述、JSON 和独立示例中保持一致；生成页面不依赖官网在线服务或用户密钥；检查鼠标/键盘/触摸与减少动态效果；记录测过的浏览器。完成以后才标为「可复制实现」，不能把一个 GitHub 链接当成已经完成的代码导出功能。

这条路线相对目前工作台需要中等程度的模块拆分和测试。批量生成 React/Vue/移动组件则有更高维护成本，应在第一种实现被验证后增加。

## 4. 插件方向备忘（当前暂缓）

插件建议先支持 Chrome/Edge 的桌面 Chromium 扩展。它负责在参考网站旁边查术语、选择元素和整理设计证据；官网负责深度预览、调参和编译。当前网页不能直接读取任意其他网站的 DOM，插件在用户主动授权的页面上可以获取相关信息。

### 阶段一：查词、截图与基础观察

- 本地打包现有词库、搜索逻辑与必要界面文案，在插件侧栏查询；点击后打开官网对应词条。
- 用户点击「观察这个元素」后读取其选择的元素；展示相关布局、字体、颜色和可读取的 CSS 值；截图与来源 URL 经用户确认后保存到本地。
- 记录得到的是哪个元素、哪个状态、什么视口与时间；区分实际读取和推断。
- 使用受控的参考 JSON 导入/导出到工作台。初期可用文件或复制内容交接，不要求登录或自动云同步。

侧栏 UI 由插件自身打包，不能把官网远程脚本直接当扩展代码加载。使用 `activeTab` + `scripting` 的主动操作方式，避免默认读取所有网站；受限页面仍不可访问。`sidePanel` 是 Chrome Manifest V3 的桌面侧栏 API。[activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab) · [sidePanel](https://developer.chrome.com/docs/extensions/reference/api/sidePanel) · [远程托管代码规则](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code)

### 阶段二：短录像与动效上下文

- 用户主动开始/停止选定标签页的短录像，默认无麦克风与声音；优先本地保存，不自动公开上传。
- 补充触发过程、视口、前后状态、可读取的 CSS/动画 API 参数与录像。
- 生成外部 AI 可阅读的参考包，明确哪些值是浏览器实际返回、哪些来自帧估算、哪些仍未知。
- 模型分析作为可选 BYOK 功能，只有用户明确操作时调用。现有 TokenDance 接入以对话流程为主，不能直接声称已支持该模型的视频输入；需另查模型能力与文件传递协议。

Chrome 提供屏幕/标签页采集机制，但视频只记录可见画面。它不能自动恢复 Canvas/WebGL 的原始数学参数、服务器规则或全部响应式约束；录制成功也不代表 AI 已准确复刻。[官方采集说明](https://developer.chrome.com/docs/extensions/how-to/web-platform/screen-capture)

阶段一的工程难度中等；阶段二还涉及媒体录制、资源清理、输入能力、包大小与失败处理，难度更高。商店上架与浏览器兼容性也需单独验证，不能因为插件源码可运行就视为已上架。

### 阶段三：与官网直接交接

网站与扩展来自不同来源，不能直接共用浏览器内存或 localStorage。可以设计严格的消息通道：只接收允许的官网来源与经过 schema、字段、体积校验的设计数据；不接受任意执行指令，不把 TokenDance Key 放在 URL 或参考包中。

扩展的消息机制可以承载同一台设备的交接，但不能自动实现不同设备间同步。[Chrome runtime 消息 API](https://developer.chrome.com/docs/extensions/reference/api/runtime)

## 5. 多端方向备忘（当前先完善 Web）

| 路线 | 能做什么 | 相对难度 / 依赖 |
| --- | --- | --- |
| 现有网页与移动布局改进 | 手机查词、体验适合触摸的案例、分享参数链接 | 增量工作较小；逐例验证 hover 的替代行为 |
| PWA | 可安装入口；经缓存设计后提供部分离线能力 | 中等；需 manifest、service worker、更新与离线状态设计，目前未实现 |
| 桌面浏览器扩展 | 浏览其他网站时查词与采集参考 | 中等至较高；浏览器权限、打包与商店流程 |
| 同机扩展 ↔ 官网交接 | 导入/导出设计参考与方案 | 中等；共享数据契约与受限消息协议 |
| 跨设备自动同步 | 电脑采集后在手机继续编辑、同步收藏 | 较高；需要用户身份和远程存储，或用户自带服务 |
| 独立移动 App | 更深入的本机文件与系统分享能力 | 较高；平台适配、发布和持续维护 |

PWA 可以沿用静态部署；安装与离线能力需要额外实现，并且不同浏览器支持存在差异。[MDN PWA 文档](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps)

GitHub Pages 可以继续承载网页和公开的审核后案例，不能自行提供私人账户与写入式云数据库。前期使用文件导入/导出与不含密钥的参数链接即可；账号和同步等真实需求出现后，可接托管身份/存储服务或用户自带后端，不必自己购买和运维服务器，但仍有服务权限、额度与成本。

保持跨端一致的应是内容 ID、参数契约、配方与验证规则，而不是强迫所有端共用同一套 UI。桌面强调采集与细调；手机强调查看、选择、快速反馈。不要把桌面扩展能力直接承诺到所有手机浏览器。

## 6. REA 方法备忘（当前不接入）

REA 为编程助手提供检查应用与运行行为的工具，相关能力通过本地工具/MCP 调用；它覆盖网站、JavaScript/Electron 和原生等目标。官方浏览器案例把用户动作、观察到的网络活动、加载的脚本与可复现结果连接起来。[REA 官网](https://rea.tools/zh-CN/) · [官方浏览器指南](https://rea.tools/zh-CN/guides/browser/) · [源码与说明](https://github.com/morluto/rea)

对 IntentKit，建议借鉴以下方法：

1. **结论附带证据。** 明确区分看见的画面、实际读取的值、推断的行为、已经实现与测过的范围。
2. **面向任务的示例。** 每个案例写用户问题、实际动作、观察、实现与验证，避免只有概念名和炫技演示。
3. **把能力开放给编程助手。** 后续可提供查词、验证参数、生成方案或读取案例的本地 CLI/MCP。它们目前只是接口方向，不是已经可调用的工具。
4. **将观察转换成方案。** 用采集证据帮助填写 Design IR 与参数建议，再让用户确认；不要声称任何网页都可自动精准反编译。

可以形成的未来流程：

```text
插件采集 / 用户提供参考 / 可选本地 REA 调查
  → 证据包（实际观察 + 未知项）
  → IntentKit 术语与意图理解
  → 用户确认的配方与参数
  → 真实预览与可复用实现
  → 重新验证
```

REA 的本地分析进程不能直接完整运行在 GitHub Pages 页面里。先采用「本地编程助手调用 REA，手动导入整理后的证据」更实际；直接联动需要单独的本地连接程序与协议。不要为 UI/UX 项目先建设原生二进制反编译平台，也不要把理解行为等同于取得第三方源码和素材的复用许可。

本次未安装或调用 REA 分析工具；只核对公开资料。现有完整源码的普通维护仍使用正常仓库工具，不需要 REA。

## 7. 当前推进顺序与完成标准

1. **本轮：Web 先闭环。** 暖金聚光与抬升使用实际 WebGL 灯光层，预览、JSON、描述和导出代码共享参数；另外 4 个受控模板沿用同一导出框架。实跑原生 Web、React StrictMode 与任意顺序视频帧后再交付 PR。
2. **本轮：维护与审核。** 双版本指南、私信提案、署名、只读 CI 与 main 保护；维护者人工收录。尚未有真实社区投稿，不虚报贡献人数或作者徽章。
3. **后续：扩充 Web 效果。** 按一套契约增加真实代码导出和验证证据，处理业务接入、兼容性与可访问性；不因为展示了某个 UI 名词就承诺它已经有通用组件。
4. **暂缓：插件、PWA / 移动端。** 本文前面的采集与多端设计只是备忘，当前不进入开发范围。
5. **暂缓：REA。** 保留证据驱动与可复现调查的借鉴方向，当前不安装、不调用、不接入 REA。

继续采用五段版本编号。路线图不等于上线承诺；每轮完成实际验证、人工审核与部署后，再发布对应版本。
