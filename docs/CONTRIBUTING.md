# IntentKit 社区贡献指南 · 给贡献者

适用项目：[Vibe-Design-Labs/Vibe-UI-UX](https://github.com/Vibe-Design-Labs/Vibe-UI-UX)。本指南依据 `0.4.1.2.1` 的真实结构编写。流程文档新增于 2026-10-12；它不是插件、代码导出或社区账号系统已经上线的公告。

**你可以提交自己的设计案例、交互效果、术语解释、译文或实现改进，并选择公开署名。所有内容由维护者决定是否收录，不自动合并。**

如果你想让 AI 帮忙，把 [AI 版指南](CONTRIBUTING_AI.md) 和 [案例提交表](contributions/TEMPLATE.md) 一起交给它。不会写代码也可以贡献，先说明你想解决的问题即可。

## 1. 先私信提案，不必先写完整代码

私信维护者：微信 **QBBai10086**，备注「IntentKit 贡献」。首次联系可以发送下面这段：

```text
我想给 IntentKit 贡献一个案例：
名称 / 一句话描述：
解决什么问题，谁会用：
我做到了哪一步：想法 / 设计稿 / 可运行演示 / 源码
参考或预览链接：没有的话写“暂无”
与现有词条有什么不同：
代码和素材是原创还是改编：
希望使用的署名：昵称 / GitHub 用户名 / 不署名
```

微信是私信渠道；GitHub Issue、Discussion、PR 正文与附件通常是公开的。公开提交只保留双方同意公开的提案摘要，不复制私人聊天、联系方式或未公开项目资料。

维护者可能回复「方向可以，继续准备」「已有相近案例，请合并思路」「需要补充说明」或「本阶段暂不收录」。**确认方向只表示可以继续准备，不代表最终接受、合并或承诺发布日期。** 没有回复时，保留你自己的作品，不将提案视为已获准收录。

不含私人资料的一般 bug 可以直接提 [Issue](https://github.com/Vibe-Design-Labs/Vibe-UI-UX/issues)。已有正式 PR 的修改意见可留在 PR 中，不需要每次重新发私信。

## 2. 哪种贡献最适合你？

| 类型 | 交什么 | 是否通常需要改代码 |
| --- | --- | --- |
| 新别名、术语解释、来源修正 | 对应词条 ID、建议文字、依据 | 通常只改词条 JSON |
| 翻译或译文审校 | 原文、译文、语言、修改理由 | 只改对应文本；机器翻译仍标草稿 |
| 已有效果的新参数方案 | 既有词条、准确参数、用途、实际演示 | 可能只需数据与案例说明 |
| 新视觉风格或交互效果 | 专属预览、参数、描述、源码与验证 | 需要注册参数和实现渲染器 |
| UX 案例 | 用户任务、起止状态、操作、反馈、限制 | 用可交互任务或状态对比，不必强加动画 |
| 已有实现仓库 | 稳定代码版本、运行方式、许可、可调参数 | 先作为提案；外部链接不自动成为官网预览 |
| 插件、跨端或新架构 | 用户场景、范围、技术依据、最小验收目标 | 先讨论范围，避免直接提交大规模重写 |

先在工作台搜索名称、别名和日常说法，避免把同一个概念做成多个近义词条。一个词条已有预览，不代表 Design Compiler 已经理解该概念；新增编译能力需要另行接入。

## 3. 可以署名，怎么署名？

在 [案例提交表](contributions/TEMPLATE.md) 中选择「署名」或「不署名」。署名可以是昵称、GitHub 用户名，以及你愿意公开的作品链接。请写清自己的贡献角色，例如概念整理、交互设计、原创实现、翻译或测试。

收录时由维护者：

1. 将案例说明保存到 `docs/contributions/<case-id>.md`，保留约定的作者显示名、链接和角色。
2. 在 [贡献记录](contributions/README.md) 中加入该案例；重要新增内容可在更新日志中注明贡献者。
3. 保留实际复用的第三方代码、字体、图片等原有版权与许可通知。案例署名不替代这些通知，也不把参考作品作者写成我们的贡献者。

GitHub 的提交作者记录与案例署名是两回事，尤其在 squash 合并时；因此不能只依靠提交历史显示作者。不要在案例里留下你的私人电话、密钥或聊天记录。**官网词条的作者徽章、作者筛选和个人主页目前未实现**，本指南先约定仓库中的署名方式。

作者同意的是其有权贡献的原创内容按本项目 MIT 许可收录，署名方式按提交表约定。改编素材保留各自已核实的许可；无法确认允许收录的素材，请改用原创替代，或只提供参考链接供讨论。GitHub 仓库公开不等于其全部代码和素材可以任意复制。

## 4. 确认方向后，准备一个可检查的案例

复制 [案例提交表](contributions/TEMPLATE.md)，填写到 `docs/contributions/<case-id>.md`。`case-id` 用稳定的小写英文和连字符，例如 `card-hover-strength-variants`。贡献记录只能由维护者在最终接受后加入，贡献者不要把自己的案例写成「已收录」。

最低提交材料：

- **用途：** 哪个用户，在什么任务中需要它；何时不适合。
- **实际行为：** 初始状态、触发、反馈、退出或取消；说明触摸、键盘和减少动态效果下的替代行为。
- **参数：** 默认值、单位、范围、实际影响的对象；哪些只是设计选择，哪些有实测依据。
- **演示：** 可运行页面或本地复现步骤。静态截图适合检查排版，不足以证明动画的时长与跟随行为。
- **来源：** 原创、概念参考或实际改编的范围；外部代码应标明具体文件与 commit/tag，以及已核实的许可。
- **证据：** 实际执行的命令、浏览器与尺寸、检查结果、未验证项；不必为了好看写成「全部通过」。
- **署名：** 显示名、角色、可选公开链接与公开同意。

只有设计稿也可以发提案。它可以进入讨论，但在完成真实预览前不进入官网可见词库。

## 5. 官网案例必须达到什么程度？

### 必须是真实、对应的专属预览

保留项目的纸张、墨绿、朱砂与手写气质作为外部工作台风格；预览内部可以按展示的设计概念改变材质与排版。不要让所有风格共用一张泛化卡片。

视觉风格需要呈现对应材质、构图或排版；动效需要实际运动与触发；UX 原则需要真实的选择、状态或任务反馈；看板可以使用明确标注的模拟数据。只有外部仓库链接或一段 GIF，仍不足以替代官网的可交互预览。

所有官网可见词条必须有真实实现，不允许 `preview: null`。构建会检查模板覆盖，但它不能判断画面是否准确；浏览器检查仍需要完成。完整要求见 [专属预览说明](PREVIEW_SCENES.md)。

### 参数、预览和描述必须一致

参数的类型、默认值、范围与枚举来自 `previews/registry.json`。词条只能覆盖已声明的参数。预览、设计描述、Agent 描述与 JSON 应使用各自流程的同一份最终参数，不要分别硬编码一套。

颜色目前只接受 `#RRGGBB`；整数数量参数可以声明 `integer: true`。不要借参数传入任意 HTML、JavaScript、SVG 或 CSS。截图中观察不到的精确时长不能编成实测结果。

### 来源与语言状态必须诚实

新词条至少准备中英文内容草稿；新的界面控件文案需要中、英、日、韩、德五语。正文缺失译文可以显式回退英文，不冒充五语已完成审校。未人工审校的内容保留 `draft`。

合并审核与知识审校是不同步骤。维护者同意合并一个草稿示例，不等于它的语言 `reviewed` 或内容 `published`。当前官网展示草稿并说明状态，不能为了让严格检查通过而批量修改这些状态。

## 6. 用 Fork 和 PR 交付

**Fork 是你的副本，PR 是请维护者检查差异的请求；它们不会自动改动官方仓库。**

1. 登录 GitHub，打开官方仓库，点击 **Fork**。
2. 在自己的 Fork 新建分支，例如 `proposal/card-hover-strength-variants`。不向官方 `main` 直接推送。
3. 编辑文件并在本地验证。没有代码改动的提案可以只包含案例说明与证据。
4. 在自己的分支提交，再推送到自己的 Fork。
5. 在 GitHub 创建 PR：base 选 **Vibe-Design-Labs/Vibe-UI-UX / main**，head 选 **你的 Fork / 贡献分支**。材料还不完整时创建 **Draft PR**，表示仍在准备。
6. 按 PR 模板说明提案摘要、文件变化、来源、署名、验证与未完成项。维护者审阅后可能要求修改或暂不收录。
7. 只有维护者决定最终收录后，才由维护者手动合并；合并进入 `main` 后现有 Pages 工作流才会检查与部署。部署失败不等于已经在官网发布成功。

开发者可使用以下命令；`YOUR_GITHUB_NAME` 要替换为自己的 GitHub 用户名：

```sh
git clone https://github.com/YOUR_GITHUB_NAME/Vibe-UI-UX.git
cd Vibe-UI-UX
git switch -c proposal/card-hover-strength-variants
npm run dev
```

项目要求 Node.js 20+；数据检查需要 Python 3。当前没有 npm 依赖，无需先 `npm install`。打开 `http://localhost:4173/studio.html`。修改源码后停止并重新启动开发服务。

检查完成后，在自己的 Fork 分支提交；只添加本次实际修改的文件：

```sh
git add docs/contributions/card-hover-strength-variants.md
git commit -m "docs: propose card hover strength variants"
git push -u origin proposal/card-hover-strength-variants
```

这只是文档提案例子。包含代码时还要添加相应源码与数据文件，不提交密钥、依赖缓存、无关输出或未说明的大文件。贡献者不自行修改发布版本、生成发布包或创建官方标签；发行工作由维护者处理。

## 7. 检查什么，怎样记录？

| 改动 | 需要检查 |
| --- | --- |
| 仅文档 | 链接与例子是否准确；修改 README 时运行 `npm run check:docs` |
| 内容、别名、译文、参数 | `npm run check:content`；涉及可见内容时在工作台检查检索、文字与对应预览 |
| 渲染器、核心逻辑、配方或控件 | `npm run check:content`、`npm test`、`npm run check:docs`、`npm run build:pages`，并完成浏览器核验 |
| 新增字体子集尚未覆盖的文字 | 按 [字体说明](FONTS.md) 重建并验证实际字体，不能只看系统回退字体 |

`npm run check:content` 已包含 `--require-previews`。现有全库草稿会产生审校警告；严格 `--publish-check` 目前会因既有草稿失败。这不要求贡献者修复整库，但新增内容的来源、状态与范围仍要准确。结构检查不证明译文、事实或许可已经核准。

涉及效果时实际检查：默认参数、最小值与最大值、退出/重播/清理、键盘与触摸、减少动态效果、小屏与桌面、不同语言的文字布局。调参后比较导出的每个参数，注明你测过的平台与未测的平台，不保证跨框架自动 1:1。

检查脚本、本地预览和打包本身不调用模型，不需要 GPT 额度。你使用其他 AI 帮忙编辑时，其自身的额度或费用另计。

## 8. 一个提案例子

**例子是待审提案，尚未新增三个正式配方：** 为已有 `hover-lift` 提供轻、中、强三种卡片反馈，复用它的真实渲染器：

| 方案 | `lift_px` | `duration_ms` | 想表达的差异 |
| --- | --- | --- | --- |
| 轻 | 3 | 180 | 克制地提示可交互 |
| 中 | 6 | 240 | 更明显的反馈；与当前词条默认值相同 |
| 强 | 9 | 300 | 用于对照强弱，不建议不分场景地使用 |

这些值都在当前注册范围内，是案例设计选择，不是行业标准。作者先私信说明用途；随后准备实际调参录像、导出 JSON 与案例说明。维护者可以选择收录为案例、要求增加正式配方接入，或认为重复而不收录。**仅写这张表不会让工作台自动多出三个按钮或三个编译配方。**

## 9. 维护者如何保证人工审核？

贡献政策要求：普通贡献者通过 Fork；不因投稿获得官方写权限；不启用自动合并机器人；每个案例由维护者决定是否收录。自动检查只提供证据，不替维护者做决定。

要在 GitHub 技术上强制执行，维护者还需要配置 `main` 的规则或分支保护：要求 PR、审核与适合的状态检查，并限制谁可以合并/推送。需要指定维护者审核时可使用 CODEOWNERS，并在规则中启用 code owner review；只有写了文档或 CODEOWNERS 文件，并不能强制这个条件。设置应保留经过确认的维护者权限与发行流程。[GitHub 官方分支保护说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

此文档不声称上述保护已启用，也不授权 AI 更改仓库权限。当前配置核查与后续功能计划见 [社区与多端方案](COMMUNITY_ROADMAP.md)。
